# Sustained HTTP stress and database recovery

Acceptance intent (not verified results until CI completes).

- Dedicated disposable service containers and local SQLite files only. Normal provider and package CI stays intact. In the dedicated job, use eight physical connections per relational runtime, bounded acquisition timeouts, and three closed-loop phases of up to 12 seconds or 16,000 attempts at concurrency 8, 32 and 128. Warm 24 keys. Mix new commands, reordered replays, hot-key traffic and mismatches. Record all status counts, transport errors, p50/p95/p99/max, elapsed throughput, sampled RSS and Node pool occupancy. Never silently retry within the timed window; recovery and durable readback happen after it using the same key.
- Every new intended key must result in one durable order; replay bytes and Location must match, mismatch must be 422 or a recognized temporary storage failure, and no unexpected responses are permitted. Report transient pressure rather than claim all requests succeeded.
- Hold all eight Node pool connections and all eight Kestrel pool connections in separate tests, assert actual exhaustion fails closed with 503 for both a fresh and existing key, release and verify the same hosts recover. The Kestrel test-only callback holds its transaction for a bounded interval.
- Stop and restart the exact GitHub Actions PostgreSQL/SQL Server service container (strict ID and image check); interrupt an active Node transaction before COMMIT, require four offline HTTP attempts to fail closed, and verify same-key replay and recovery on the original app processes after restart. Verify the interrupted write did not commit. Never remove/recreate the database or change its durability configuration.
- SQLite uses real local files, not in-memory databases. The prior file-permission, checkpoint, backup/restore and constrained page-cap tests remain the storage fault evidence; no relational-server restart applies to SQLite.
- References: [PostgreSQL 17 shutdown](https://www.postgresql.org/docs/17/server-shutdown.html), [SQL Server container data persistence](https://learn.microsoft.com/en-us/sql/linux/sql-server-linux-docker-container-configure), [SQLite WAL](https://www.sqlite.org/wal.html).
- Shared CI runners are not production hardware. This is bounded closed-loop stress, not a long soak or memory-leak proof, not a capacity/SLO promise, not physical disk exhaustion, power loss, multi-region failover or a dropped COMMIT acknowledgment test. Node relational RSS includes the test client. No optimization will weaken transaction safety or change the wire contract.

[PR #16](https://github.com/Ahmad09ha/IdempotencyKit/pull/16) passed [all three dedicated jobs](https://github.com/Ahmad09ha/IdempotencyKit/actions/runs/45511557572) on `def10e63166b0540129843a67d1e95b28f2930b4`: 251,805 timed attempts, 236,065 HTTP 201, 15,740 intentional 422, 15,884 distinct committed orders including warm-ups; no unexpected statuses or transport failures in those timed windows. Four pool-exhaustion cases and both actual relational database stop/start cases passed, as did all three read-only reports. Merged as `158e656`; all eight [post-merge workflows](https://github.com/Ahmad09ha/IdempotencyKit/actions/runs/45512074692) passed. Node wait queues reached 119/120 with an eight-connection pool. These cap-limited tests do not prove absence of leaks. See [final readiness](FINAL_RELEASE_READINESS.md) for extended time-based and isolated storage testing.
